# uwuFlights Telegram Bot: Plan

This directory is still a placeholder. Nothing has been built yet; this is
the confirmed plan for a future companion Telegram bot, to be implemented
with Telethon (Python) once you're ready. It will run standalone on your
Debian 13 VPS under `tmux`, with its own SQLite database (no dependency on
the web app's Supabase project).

## Why a bot, on top of the web app

The web app (`main-site`) is point-and-search: you open it while you're
already looking at the sky. A bot is push-based: it can tell you about
something interesting before you go looking, and it can hold a
conversation to set that up.

## Stack

- **Telethon** (Python), running as a bot via a bot token from BotFather.
- **SQLite**, for everything that needs to persist: watches, subscription
  state, turn-based conversation progress, and interactive button state.
  SQLite is also used for scheduling (a polling loop reads due rows
  instead of relying on an in-process scheduler), so nothing is lost on
  restart.
- No shared database with `main-site`. This bot's SQLite file is its own
  source of truth; it does not read or write the web app's Supabase
  tables.
- Replies use rich formatting (Markdown/HTML parse mode) with inline
  buttons throughout, not plain text.

## Commands

| Command | Behaviour |
|---|---|
| `/start` | About the bot, the full command list, and two buttons: open the uwuFlights web app, and the Buy Augy a Coffee donation link. |
| `/sub` | Master switch: resume alert delivery for every watch this chat has. |
| `/unsub` | Master switch: pause alert delivery for every watch this chat has, without deleting them. |
| `/watch` | Turn-based setup for a new area watch (see below). |
| `/fact` | Replies with a random fact. |
| `/mywatches` *(suggested)* | Lists this chat's active watches, each with its own persistent Stop button. |
| `/cancel` *(suggested)* | Aborts an in-progress `/watch` setup if the user gets stuck partway through. |

No command name mentions the bot's own name. The command list itself will
be set manually via BotFather's `/setcommands`, not generated by the bot;
`setup.md` (once building starts) will document exactly what to paste in
there.

### `/watch` flow (turn-based)

1. Bot asks for a location. The user either types `lat, lon` or shares a
   Telegram location.
2. Bot shows manufacturer buttons (Airbus, Boeing, and so on).
3. Tapping a manufacturer shows that manufacturer's model buttons
   (multi-select: tapping toggles a model on/off, with a Done button to
   confirm the selection).
4. Bot shows radius buttons (for example 10 / 25 / 50 / 100 km).
5. Bot confirms and saves the watch to SQLite, replying with a persistent
   Stop button tied to that row's ID, so it keeps working even after a
   bot restart.

Progress through this flow is written to SQLite after each step (not kept
only in memory), so a bot restart mid-setup does not strand the user; they
can resume or use `/cancel` to start over.

### Sending a bare location (not mid-`/watch` setup)

If a user just shares their location outside of an active `/watch` setup,
the bot replies with two buttons:

- **Check now**: an instant one-off reply listing aircraft currently near
  that point (this is what a `/noise`-style command would have done).
- **Start a watch here**: jumps into the `/watch` flow with that location
  already filled in.

### Persistent interactive buttons

Every message with buttons (Stop-watch buttons, the manufacturer/model
picker, the Check now / Start a watch here prompt, and so on) has its
callback data resolved against a SQLite table rather than in-memory state,
so buttons sent before a restart keep working exactly as before after the
bot comes back up.

## Draft SQLite schema

```sql
create table users (
  chat_id integer primary key,
  subscribed integer not null default 1,
  created_at text not null default (datetime('now'))
);

create table watches (
  id integer primary key autoincrement,
  chat_id integer not null references users(chat_id) on delete cascade,
  lat real not null,
  lon real not null,
  radius_km integer not null,
  aircraft_types text not null, -- JSON array of ICAO type codes
  active integer not null default 1,
  created_at text not null default (datetime('now'))
);

create table watch_setup_state (
  chat_id integer primary key references users(chat_id) on delete cascade,
  step text not null,
  data_json text not null,
  updated_at text not null default (datetime('now'))
);

create table buttons (
  chat_id integer not null,
  message_id integer not null,
  callback_data text not null,
  context_json text not null,
  created_at text not null default (datetime('now')),
  primary key (chat_id, message_id, callback_data)
);

create table scheduled_jobs (
  id integer primary key autoincrement,
  chat_id integer not null,
  run_at text not null,
  job_type text not null,
  payload_json text not null,
  done integer not null default 0
);
```

## `/fact` data source

`/fact` calls [Useless Facts](https://uselessfacts.jsph.pl/)
(`GET https://uselessfacts.jsph.pl/api/v2/facts/random`). It's general
trivia rather than aviation-specific, but that matches the original brief
("quotes or facts or etc") and needs no signup or API key, consistent with
every other data source across this project.

Planned safeguards, matching the pattern already used in
`main-site/api/adsb.js` and `main-site/api/opensky.js`:

- an upstream timeout so a slow response doesn't hang the reply,
- defensive parsing (missing/renamed fields fall back to a generic
  "couldn't fetch a fact right now, try again shortly" reply instead of
  crashing),
- a short local cache of the last few facts so repeated `/fact` calls in
  quick succession, or a temporary upstream outage, don't just fail
  outright.

A `/trivia` command was considered using Open Trivia Database, but was
dropped: that API has no dedicated aviation category (the closest,
Vehicles, mixes in cars, boats, and trains) and there's no way to filter
it down further, so it didn't fit the app's aviation focus.

## Hosting

This bot needs an always-on process, unlike the web app. Plan is to run it
with Telethon's long-polling under `tmux` on your Debian 13 VPS, so it
survives SSH disconnects and can be reattached to for logs and restarts.

## What gets delivered once building starts

Individual files (not a zip): `bot.py` (or a small module split), the
SQLite schema as a `.sql` file, `requirements.txt`, `.gitignore`,
`README.md` (what the bot does and how to use it), and `setup.md`
(BotFather setup: name, about text, description, command list, and
privacy mode).

## Status

Planning only, confirmed with you on 2026-07-25:

- `/sub` and `/unsub` are a master on/off switch for all of a chat's
  watches, with room to add per-watch toggles later.
- A bare location message asks the user to choose between an instant
  check and starting a new watch there, rather than assuming either one.
- `/fact` is its own command, not folded into `/start`.
- The aircraft-type picker in `/watch` is a manufacturer drill-down
  (manufacturer buttons, then that manufacturer's model buttons), not a
  flat shortlist or category-only picker.
- No `/help` command; the command list and descriptions are set up
  manually through BotFather's `/setcommands` instead.
- `/fact` uses the Useless Facts API. A `/trivia` command using Open
  Trivia Database was considered and dropped, since that API has no
  dedicated aviation category.

No code, dependencies, or the SQLite file itself have been created yet.
